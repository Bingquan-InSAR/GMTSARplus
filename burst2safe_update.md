# GMTSAR Compatibility with Burst-Level Sentinel-1 Products

## 1. Scope

This document records a GMTSAR-side compatibility limitation encountered when processing burst-level Sentinel-1 SAFE products generated by `burst2safe`. The observed issues concern the `sliceList` XML element and the `numberOfSamples` metadata field after burst assembly.

## 2. Controlled Script Comparison

| Script | Source | Input | Result |
| --- | --- | --- | --- |
| `create_frame_tops.csh` | Official GMTSAR | Identical burst SAFE list | Segmentation fault |
| `GMTSAR_s1_createTOPSframes.csh` | pSAR workflow | Identical burst SAFE list | Segmentation fault |
| `GMTSAR_s1_createTOPSframes_burst.csh` | Modified in GMTSAR+ | Identical burst SAFE list | Completed successfully and generated the frame-level SAFE |

The first two scripts are conventional frame-assembly workflows. The third was adapted for burst-level product structure and metadata.

## 3. GMTSAR+ Compatibility Adjustments

### 3.1 Empty `sliceList` element

The affected XML field is `imageAnnotation/imageInformation/sliceList`.

The original burst annotation contains:

```xml
<sliceList count="0">
</sliceList>
```

During frame assembly, the official GMTSAR and pSAR scripts generated:

```xml
<sliceList count="0">
```

When this annotation is processed by GMTSAR `make_s1a_tops`, the program terminates with a segmentation fault. GMTSAR+ closes the element as:

```xml
<sliceList count="0"></sliceList>
```

### 3.2 `numberOfSamples` metadata

The second affected field is `imageAnnotation/imageInformation/numberOfSamples`.

When multiple bursts are assembled into one frame, GMTSAR+ sets this field to the maximum sample width among the selected bursts:

```python
image_information.find('numberOfSamples').text = str(
    max(cast(int, info.width) for info in self.burst_infos)
)
```

This makes the declared sample dimension consistent with the assembled frame rather than with one individual burst.

### 3.3 Scope of the adjustments

The `sliceList` normalization and `numberOfSamples` assignment are independent metadata corrections. The former ensures a complete empty XML element; the latter ensures that the declared sample dimension matches the assembled burst frame.

These adjustments are applied after frame assembly and modify only XML metadata required for structural and dimensional consistency. They do not modify timing, orbit, geolocation, calibration, phase, amplitude, or measurement values.

The diagnostic and normalization commands are:

```csh
grep -Hn '<sliceList count="0">' $outdir/$newname/annotation/*.xml

foreach f ($outdir/$newname/annotation/*.xml)
    sed -i.bak 's#<sliceList count="0">#<sliceList count="0"></sliceList>#g' "$f"
    rm -f "$f.bak"
end
```

Relevant modules:

```text
GMTSAR_s1_createTOPSframes_burst.csh  burst-oriented frame assembly
make_s1a_tops                         Sentinel-1 XML/TIFF processing
assemble_tops                         burst/frame assembly
gmtsar_preproc_batch_tops_esd.csh     downstream SLC and ESD processing
```

The pSAR script `pSAR_gmtsar_s1.py` orchestrates the workflow and calls the burst-oriented script; it does not independently generate the Sentinel-1 annotation metadata.

## 4. Minimal Reproducible Example

```bash
GMTSAR_s1_createTOPSframes_burst.csh \
    SAFE_filelist_20250918 \
    /path/to/S1A_OPER_AUX_POEORB_OPOD_20251008T070612_V20250917T225942_20250919T005942.EOF \
    20250918_twopins.ll \
    1 \
    /path/to/cebu/raw
```

Here, `1` denotes VV polarization. The same input files were used for all three scripts in Section 2.

| Condition | Result |
| --- | --- |
| Without XML normalization | `Segmentation fault` |
| With `sliceList` normalization only | XML structure corrected |
| With both compatibility adjustments | Processing completed successfully |

The successful result requires both the structural correction of `sliceList` and the dimensional correction of `numberOfSamples`.

## 5. Upstream Verification

```text
Repository: https://github.com/ASFHyP3/burst2safe
Release: v2.0.3
Commit: b5436cea79885bf95bc49114060b906392741917
```

The checked upstream code creates a complete empty `sliceList`. No GMTSAR-specific compatibility adjustment was found at this commit. The upstream implementation also does not provide the GMTSAR-side post-assembly correction of `numberOfSamples` described above. This does not indicate a defect in `burst2safe`; it confirms that these are downstream GMTSAR+ compatibility measures.

## 6. Relevance to GMTSAR+

These adjustments should not be interpreted as a new SAR data-download method. Sentinel-1 data search and downloading are provided by existing services and tools. The GMTSAR+ contribution documented here is the adaptation of burst-derived Sentinel-1 SAFE products to the GMTSAR-SBAS workflow, including:

- burst-oriented frame assembly;
- reconstruction of a GMTSAR-compatible SAFE-like structure;
- correction of incomplete `sliceList` XML elements;
- correction of assembled-frame `numberOfSamples` metadata; and
- integration with downstream GMTSAR processing.

This is a compatibility and workflow-integration contribution rather than a new interferometric or SBAS algorithm.
